# ADR-001 · PostgreSQL con una base por servicio

- Estado: **Aceptado**
- Fecha: 2026-09-23

## Contexto

AE1 persistía en SQLite (una sola mesa de `mesas` en un archivo `/dev/shm`). AE2 requiere concurrencia real, integridad bajo carrera y, sobre todo, la regla de **cero SQL cruzada**: cada dominio (mesas, builds, feed, notificaciones) debe tener su propio esquema persistente, sin que un servicio consulte tablas de otro. Se necesitaba un motor con locks a nivel fila, `SERIAL`/`BIGSERIAL` controlado, timestamps con zona horaria y soporte multi-database en una sola instancia.

## Decisión

Migrar a **PostgreSQL 16-alpine (postgres:16-alpine)** con **una base por servicio** dentro de la misma instancia:

- `mesas_db`, `builds_db`, `feed_db`, `notif_db` (más `*_test` para la suite pytest) creadas de forma idempotente en `infra/postgres-init/01-crear-dbs.sql`.
- Cada servicio mantiene su propio `ConnectionPool` de psycopg (B02) apuntando solo a su DB, con `row_factory=dict_row`.
- Identidad con `GENERATED BY DEFAULT AS IDENTITY`, timestamps `TIMESTAMPTZ DEFAULT now()`.
- La barrera atómica de cupos usa `UPDATE ... WHERE jugadores_actuales < jugadores_max RETURNING id` (ver ADR-004).

## Consecuencias

- **Positivas**: integridad real bajo concurrencia (locks de fila), gates por columna (`CHECK`), tipado fuerte de fechas y documentos por servicio; un solo contenedor de base reduce costos de operación.
- **Negativas**: un postgres caído tira los 4 servicios (mitigado por `/ready` degradado y arranque con `depends_on: service_healthy`); requiere inicializar esquemas por servicio (los `init_db` corren en el lifespan de cada uno); los tests necesitan bases `*_test` dedicadas para no pisar el ambiente dev.
